# 🔬 应急响应平台 — 深度优化建议（20 条）

> **编制**：架构评审组 | **日期**：2026-07-13
> **范围**：基于上一轮 17 项优化后的代码库二次扫描
> **方法**：56 个测试文件 + 40+ 个后端模块 + 29 个前端组件逐一审查

---

## 一、安全加固（#1-#4）

---

### P0 #1 默认管理员凭据硬编码

**现状**：`config.py` L47-48 直接写死 `DEFAULT_ADMIN_USER: str = "admin"` 和 `DEFAULT_ADMIN_PASSWORD: str = "admin123"`。任何获取源码的人都知道初始密码。

**代码位置**：`backend/app/config.py` L47-48

**建议**：
- 默认密码改从环境变量 `IR_DEFAULT_PASSWORD` 读取
- 首次启动时强制修改密码（加 `must_change_pwd` 标记）
- `_create_default_admin()` 中检测环境变量未设置则生成随机密码并打印

---

### P0 #2 SECRET_KEY / AI_ENCRYPTION_KEY 固定回退值

**现状**：`config.py` L37-40 的 `SECRET_KEY` 和 L56-59 的 `AI_ENCRYPTION_KEY` 都有硬编码的默认字符串。生产环境忘记设置环境变量即可被伪造 JWT 或解密 AI API Key。

**代码位置**：`backend/app/config.py` L37-40, L56-59

**建议**：
- 启动时检测是否使用默认密钥，打印高亮 WARNING 日志
- 生产环境缺少环境变量则阻止启动（或至少警告）
- 文档中强调生产部署必须设置 `IR_SECRET_KEY` 和 `IR_AI_ENCRYPTION_KEY`

---

### P0 #3 登录端点无速率限制

**现状**：`/api/auth/login` 无任何暴力破解防护，攻击者可无限尝试密码。

**代码位置**：`backend/app/api/auth.py`

**建议**：
- 集成 `slowapi` 库，对同一 IP 每 5 分钟最多 10 次失败尝试
- 连续 5 次失败后锁定账号 15 分钟
- 记录失败登录日志到审计表

---

### P2 #4 审计日志缺少完整性保护

**现状**：AI 审计日志记录 prompt/response，但没有哈希链或数字签名。数据库管理员可修改记录不留痕迹。

**代码位置**：`backend/app/models/ai_audit_log.py`

**建议**：
- 每条审计记录增加 `hash_chain` 字段：`SHA256(prev_hash + content)` 
- 写入时校验前一条 hash，形成不可篡改的链式结构
- 前端可选择性展示审计链验证状态

## 二、数据库性能（#5-#8）

---

### P0 #5 25+ 张表严重缺少索引

**现状**：整个数据库仅 **6 个索引**。`abnormal_processes`、`suspicious_connections`、`timeline_events`、`ioc_hits` 等主要分析表**全无 host_id 索引**。所有查询都通过 `WHERE host_id=?` 过滤，数据量达到万级后每次全表扫描。

**代码位置**：`backend/app/database.py`

**建议**：为高频查询字段加索引：
```sql
CREATE INDEX idx_abnormal_processes_host ON abnormal_processes(host_id);
CREATE INDEX idx_suspicious_connections_host ON suspicious_connections(host_id);
CREATE INDEX idx_timeline_events_host ON timeline_events(host_id, timestamp);
CREATE INDEX idx_ioc_hits_host ON ioc_hits(host_id);
CREATE INDEX idx_persistence_items_host ON persistence_items(host_id);
CREATE INDEX idx_rules_enabled ON rules(enabled, category);
CREATE INDEX idx_ai_analysis_reports_host ON ai_analysis_reports(host_id, is_latest);
```
**收益**：减少 90%+ 全表扫描。

---

### P1 #6 每次分析新建 12+ 次数据库连接

**现状**：`get_connection()` 每次调用都 `sqlite3.connect()` → `close()`。`AnalysisService.analyze()` 中 12 个 `batch_create` 各自独立开连接 - 提交 - 关闭，事务开销巨大。

**代码位置**：`backend/app/database.py` L534-556 + `models/analysis.py`

**建议**：
- 改用 `threading.local` 实现线程级连接缓存（单例模式）
- `analyze()` 中开启统一事务，传入 `conn` 参数避免重复连接
- 或实现简单的连接池（SQLite 的 `check_same_thread=False` + 队列）

---

### P1 #7 batch_create 逐条 INSERT 性能差

**现状**：每个 `batch_create` 内部 `for item in items: conn.execute(...)`。对 500+ 条记录的场景，N 次独立 INSERT 比单次 `executemany` 慢 10-50 倍。

**代码位置**：`backend/app/models/analysis.py`（14 个 batch_create 方法）

**建议**：
- 全部改为 `conn.executemany()` 批量执行
- 示例：`conn.executemany("INSERT INTO table(col1,col2) VALUES(?,?)", items)`
- 每 500 条分批提交（避免单事务过大）

---

### P1 #8 规则效能统计缺历史趋势

**现状**：刚加了 `hit_count` / `last_hit_at` / `avg_risk_score`，但缺少每小时/每日的命中时间序列。无法回答"这条规则今天早上突然暴增还是平稳下降"。

**代码位置**：`backend/app/database.py` + `backend/app/rules/rule_engine.py`

**建议**：
- 新建 `rule_hit_history` 表：`{rule_name, hour_bucket(datetime), hit_count, avg_score}`
- `_update_rule_stats()` 批量更新时同步写入时间序列
- 前端规则管理页"效能"Tab 新增命中趋势折线图

## 三、大文件拆分（#9-#12）

---

### P1 #9 rule_engine.py 2,609 行 — 需拆为模块包

**现状**：`rule_engine.py` 2,609 行 / **112.8 KB**，是项目最大的文件。混合了模块级常量（_C2_FRAMEWORK_SIGNATURES 等）、20+ 个辅助函数、RuleEngine 类（含 6 种规则类型的分发）、累加评分逻辑。

**代码位置**：`backend/app/rules/rule_engine.py`

**建议**：拆分为模块包：
```
rules/
  __init__.py         # 导出 RuleEngine
  constants.py        # BEHAVIOR_PATTERNS, 端口/路径常量
  helpers.py          # _norm_proc_name, _levenshtein, _parse_datetime
  matching/
    __init__.py
    regex_matcher.py   # _match_regex
    list_matcher.py    # _match_list（含 IOC 动态合并）
    behavior_matcher.py# 35 个 _match_* 行为匹配器
    composite_matcher.py
    threshold_matcher.py
    exists_matcher.py
  engine.py           # RuleEngine 主类（evaluate/dispatch）
  scoring.py          # 累加评分、置信度计算
```
**收益**：每个文件 200-400 行，测试更聚焦，可单独 mock。

## 四、代码质量（#13-#16）

---

### P2 #13 严重度权重定义重复 + 评分去重

**现状**：
- `anomaly_detector.py` L12-18：`SEVERITY_SCORES`
- `risk_assessor.py` L16-22：`SEVERITY_WEIGHTS`
- 两处值相同但定义位置不同，同步易遗漏
- `_apply_accumulated_scoring` 与 `_apply_connection_scoring` 中约 40 行评分循环代码重复

**代码位置**：`backend/app/analysis/anomaly_detector.py` + `backend/app/analysis/risk_assessor.py`

**建议**：
- 统一到 `shared/severity.py`：`SEVERITY_WEIGHTS = {"critical": 35, "high": 20, "medium": 10, "low": 5, "info": 1}`
- 抽取公共函数 `_aggregate_scoring(matches, rule_label_map, global_context) → list`

---

### P2 #14 14 个 batch_create 方法 — 基类化模板方法

**现状**：14 个 `batch_create` 方法的模式几乎完全相同：
```python
if not items: return 0
with get_connection() as conn:
    conn.execute("DELETE FROM ... WHERE host_id=?", [host_id])
    for item in items:
        conn.execute("INSERT INTO ... VALUES(...)", [...])
    conn.commit()
```
每个约 25-35 行重复模板。

**代码位置**：`backend/app/models/analysis.py`

**建议**：
- 新建 `BaseAnalysisModel.batch_create(host_id, items, table, columns, transformer=None)`
- 使用 `conn.executemany()` 替代逐条 INSERT
- 减少约 300 行重复代码

---

### P2 #15 dashboard.py 15 次独立 SQL — 需缓存

**现状**：`/api/dashboard/stats` 中约 15 次独立 SQL 查询（每个指标/趋势/分布各一个），都在单一 `get_connection()` 中串行执行。多用户并发时，每次请求都产生大量数据库开销。

**代码位置**：`backend/app/api/dashboard.py`

**建议**：
- 仪表盘查询结果缓存到内存字典，TTL=60s
- 合并多个 COUNT：`SELECT (SELECT COUNT(*) FROM x) as a, (SELECT COUNT(*) FROM y) as b`
- 预计算规则排行并存储到汇总表

---

### P2 #16 API 响应格式不一致

**现状**：`knowledge_draft.py` 直接编写 `{"code": 0, "data": ..., "message": "success"}`，而其他 API 文件可能返回不同格式。前端需要适配多种响应结构。

**代码位置**：`backend/app/api/knowledge_draft.py` 等

**建议**：
- `api/__init__.py` 中定义 `ResponseHelper` 类（含 `ok()`, `fail()`, `paginated()`）
- 所有 API 模块统一调用
- 自动序列化异常捕获

## 六、运维与配置（#19-#20）

---

### P2 #19 config.py 缺少生产环境配置项

**现状**：`config.py` 缺少以下生产环境必需的配置项：
- 无 `LOG_LEVEL` 配置（当前写死 DEBUG 级别？）
- 无 `SWAGGER_ENABLED`（生产环境应关闭 API 文档）
- 无 `DB_TIMEOUT`（SQLite 超时默认值可能太短）
- 无 `CORS_ORIGINS` 列表（当前硬编码）

**代码位置**：`backend/app/config.py`

**建议**：新增配置项：
```python
LOG_LEVEL: str = os.environ.get("IR_LOG_LEVEL", "INFO")
SWAGGER_ENABLED: bool = os.environ.get("IR_SWAGGER_ENABLED", "true").lower() == "true"
DB_TIMEOUT: int = int(os.environ.get("IR_DB_TIMEOUT", "30"))
CORS_ORIGINS: list = os.environ.get("IR_CORS_ORIGINS", "*").split(",")
```
