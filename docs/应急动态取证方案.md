# 应急动态取证方案（IR 专家视角）

> 文档定位：针对「daemon 实时推流是否应接入分析中心」的应急专家结论与完整落地方案。
> 适配平台版本：commit `0532fb7`（2026-08-08 状态）
> 作者视角：安全应急响应（Incident Response）专家

---

## 0. 结论先行

**不建议把 daemon 全量实时数据持续灌入「分析中心」。**

更优方案是「**实时检测 + 事件驱动动态取证（Dynamic Triage）**」两段式架构：

- **实时段（已具备）**：daemon 实时进程流 → 告警引擎 → 统一告警中心 → 事件聚类 → `events` 表 → 分析中心（事件维度）。负责"发现"。
- **取证段（新增）**：告警/调查触发时，向指定主机 daemon 下发**定向采集任务**，结果写入对应专用表并在分析中心实时呈现。负责"取证"。

核心理由：实时流的价值在"快"，分析中心的价值在"全 + 准"；把未归一化的原始事件汤硬塞进需要多源关联的鉴证工作台，既淹没研判又污染存量数据。应急场景应让两类数据消费各司其职。

---

## 1. 方法论：应急数据消费分层

| 消费类型 | 目标 | 数据要求 | 时效 | 典型载体 |
|----------|------|----------|------|----------|
| **检测 / 发现** | 在攻击进行中捕获异常 | 增量、原始、未归一即可 | 秒级 | 实时告警、心跳、进程事件流 |
| **取证 / 研判** | 还原时间线、攻击链、根因 | 完备、归一、可交叉关联 | 分钟~小时级 | 快照、导入包、定向取证结果 |

任何把"检测流"直接当"取证源"的设计，都会产生**事件汤（event soup）**——海量低价值增量淹没高价值取证视图，且在应急高压下干扰决策。正确做法是：检测流触发告警，告警驱动**按需、定向、scoped**的取证采集。

---

## 2. 现状诊断（基于代码实测）

### 2.1 daemon 实际推了什么

`run_daemon`（`agent/agent.py:311-325`）调用 `_collect_incremental`（`agent/agent.py:224-248`）推流。该函数**只接收 `collect()` 返回 `list` 的采集器**，返回 `dict` 的采集器被整段 `continue` 跳过。

`_DAEMON_COLLECT_INTERVALS` 声明 4 个增量采集器，实测：

| 增量采集器 | 间隔 | `collect()` 返回 | 行号 | 进推流？ |
|-----------|------|----------------|------|---------|
| `process_events` | 5s | **list** | process_events.py:75 | ✅ 是 |
| `network` | 30s | dict | network.py:24 | ❌ 跳过 |
| `files` | 10s | dict | files.py:48 | ❌ 跳过 |
| `logs` | 60s | dict | logs.py:62 | ❌ 跳过 |

**事实 1**：daemon 当前实际只推**进程事件流 + 心跳**。日志里 `Collected 275 TCP / 28 file hashes` 只是各 collector 内部 `logger.info`，返回的 dict 在 `_collect_incremental` 被丢弃，**未推平台**。

**事实 2**：进程事件推流时，`_collect_incremental`（`agent.py:243`）执行 `item["event_type"] = name`，把原始事件类型整体覆盖成采集器名（`process_events`）。而后端 `list_process_starts`（`process_event.py:131`）只筛 `event_type == "process_start"`，导致 daemon 进程事件**进不了归一化 / 根因 / 进程树**——只有实时告警引擎用的是原始 payload，所以告警能触发，深度分析吃不到。

**事实 3**：分析中心（store `stores/analysis.js` 全 import `@/api/events`）读 `events` 表（告警聚类结果），不读 `process_events` 表；且 `analyze_host`（`api/analysis.py:28`）要求 `host.status ∈ ("imported","analyzed")`，daemon 常驻主机点不了"分析"。

## 3. 总体架构（两段式）

```
[实时段 · 已具备]                         [取证段 · 新增]
主机 daemon ─进程事件(5s)+心跳(30s)→ 后端接收 ─→ AlertEngine 实时评估
                                          │
                                          └─→ 统一告警中心(WebSocket) → 事件聚类 → events 表 → 分析中心(事件维)

平台「发起取证」─命令通道(轮询 tasks)→ daemon 定向采集(triage)
                                          │
                                          └─→ 分流写入 file_hashes / network_connections /
                                              process_events / logs ─→ 分析中心(实时取证视图)
```

两条段最终汇入同一个「分析中心 · 统一研判工作台」（事件时间线 + 攻击链 + 根因 + 进程树）。

## 4. 详细设计

### 4.1 阶段一：轻量打通（1–2 天）

**改动 1 · 修复 `event_type` 覆盖**
- 位置：`agent/agent.py:243`
- 现状：`item["event_type"] = name` 覆盖原始类型。
- 改动：保留原始 `event_type`，新增 `source` 字段记录采集器名（如 `source="process_events"`）。后端 `ProcessEventConsumer.normalize` 无需改动。
- 验收：daemon 主机进程事件进入根因分析 / 进程树。

**改动 2 · 放宽 `analyze_host` status 限制**
- 位置：`backend/app/api/analysis.py:28`
- 改动：白名单加入 daemon 常驻状态（或改为"已注册主机即可分析"）。
- 验收：daemon 常驻主机可正常触发"分析"。

### 4.2 阶段二：动态取证任务（3–5 天）

核心新增。需先确认**命令下行通道**（现状 daemon 仅单向推流）。

| 方案 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| **A（推荐）** | daemon 每 30s 轮询 `GET /api/hosts/{id}/triage-tasks` | 无长连、最小依赖、易回退 | 任务下发有 ≤30s 延迟 |
| B | 复用 WebSocket/SSE 下行 | 近实时 | 需 daemon 维持长连，复杂度高 |

**改动清单（以方案 A 为例）：**

1. **后端 · 任务接口（新增）**
   - `POST /api/hosts/{id}/triage-tasks`：创建任务，`scope` 限定采集项（`file_hashes` / `network` / `process_subtree` / `security_logs`）。
   - `GET /api/hosts/{id}/triage-tasks`：daemon 轮询拉取 + 平台查询状态。
   - 鉴权复用 `get_current_agent` + `assert_host_binding`。
2. **daemon · triage 执行器（新增 `agent/collectors/triage.py`）**
   - 按 scope 调用已有采集器做**定向**采集，返回 **list**（避免重蹈 `network/files` 返回 dict 被跳过的覆辙）。
   - 结果按 `event_type` 分流写入 `file_hashes` / `network_connections` / `process_events` / `logs` 专用表。
3. **前端 · 触发与呈现**
   - 分析中心 / 主机详情增加「发起取证」按钮。
   - 取证结果自动聚合到该主机实时取证视图（时间线 / 外连 / 文件哈希 / 进程子树）。

**验收**：统一告警中心点开告警主机 → 发起取证 → 该主机 `C:\Users\Public` 文件哈希、当前外连、进程子树出现在分析中心实时取证视图。

### 4.3 阶段三：聚合稳定性（收尾，1 天）

- 核对 `AlertEngine.evaluate_events` → 聚类 → `events` 写入的**幂等/去重**，避免 daemon 高频进程流产生告警风暴。
- 验收：daemon 命中告警稳定、不重复地进入分析中心事件维度。

---

## 5. 数据模型要点

- 取证数据打 `source="triage"` 标记，与快照数据（`source="snapshot"`）可区分，互不污染。
- `process_events` 表保留 `source` 字段区分 `daemon` 实时流与 `triage` 取证流。
- 所有取证写入复用现有专用表结构（`file_hashes` / `network_connections` / `logs` 等），**不新增冗余表**。

---

## 6. 风险、回退与验收

| 风险 | 应对 |
|------|------|
| `event_type` 改动影响归一化/告警 | 单测覆盖 + 灰度；保留 `source` 兼容旧数据 |
| 命令通道增加 daemon 复杂度 | 阶段二方案 A 为可选能力，可配置关闭 |
| 取证写入污染存量分析 | 打 `source=triage` 标记，与快照数据区分 |

每阶段独立可验收、可回退；无阶段一/二不可逆的表结构变更。

---

## 7. 专家评判：为何否决"全量实时推流"

1. **违背数据消费分层**：实时流用于发现，取证需完备可关联，二者不可混用。
2. **技术走不通**：实测 daemon 仅推进程事件；即便全推，`event_type` 覆盖 + `analyze` 限制 + 分析中心读 `events` 表三重障碍需改 4 处以上，且推上去的数据因未归一、缺专用表，仍无法支撑深度分析。
3. **噪声高、收益低**：全量持续写入会淹没研判视图，且存储/算力浪费在多数无调查价值的增量上。
4. **动态取证更优**：按需、定向、scoped、新鲜——既获实时性，又保证可归一化与关联，只有有调查价值时才占用资源。
