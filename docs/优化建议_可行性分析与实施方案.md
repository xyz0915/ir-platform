## 二、仪表盘设计分析

### 2.1 设计概览

仪表盘 HTML 原型是一份**全局态势感知页面**，含 4 个区域：

| 区域 | 内容 | 数据来源 |
|------|------|----------|
| **指标卡片** | 待处理告警（23）、活跃案件（12）、已采集主机（47）、知识库命中（186） | 需新增聚合查询 |
| **案件趋势图** | 最近 7 天案件数量堆叠柱状图（高危/中危/低危） | 需按天聚合 `cases` 表 + `analysis_results` |
| **风险分布饼图** | 全部已分析主机的风险等级占比 | `analysis_results.risk_level` 聚合 |
| **底部表格** | 待处理告警列表 + 最近采集主机网格 | `cases` + `hosts` 表联表查询 |

### 2.2 可行性评估

| 方面 | 状态 | 分析 |
|------|------|------|
| 前端实现 | ✅ **可行** | 当前无 DashboardView.vue，需新建。原型 HTML 直接使用 ECharts + 纯 CSS，Vue 移植成本低（约 1 天） |
| 后端 API | ✅ **基本可行** | `cases` 和 `analysis_results` 表已存在，但缺少按天聚合 + 告警状态聚合接口，需新增 1-2 个 REST 端点 |
| 实时数据 | ⚠️ **待定** | 当前分析是"按需触发"而非持续采集。指标卡片中的"待处理告警 23"需定义什么是"待处理" |
| 预警推送 | ❌ **当前不支持** | 仪表盘的"刷新"是主动查询，无 WebSocket 推送。但一期可以轮询，二期再加推送 |

### 2.3 实施建议

**结论**：仪表盘是**有价值但非紧急**的增强功能。当前平台的核心工作流是"采集→分析→处置"，缺少 Dashboard 不影响核心流程。建议放在 **P2 二期**实施。

具体方案：
1. 新增 `frontend/src/views/DashboardView.vue`（移植原型 HTML）
2. 新增 `backend/app/api/dashboard.py`（聚合查询 4 个端点）
3. 路由 `/dashboard`，设为登录后默认首页
4. 数据刷新间隔 30 秒（轮询）

### #1 分析管道并行化

| 维度 | 评估 |
|------|------|
| **优先级** | 🔴 P0 |
| **代码可行性** | ✅ **高** |
| **代码量** | ~40 行 |
| **实施成本** | 低（< 0.5 天） |
| **收益** | 🔥 分析耗时 5-10s → 2-4s |

**现状确认**：
`analysis_service.py` L184-235 中，进程检测、连接检测、启动项检测、注册表提取各步骤**严格串行**，各自调 `batch_create` 写库后才到下一步。

```python
# L185: 进程检测 → batch_create
abnormal_processes = AnomalyDetector.detect_processes(...)
AbnormalProcess.batch_create(host_id, abnormal_processes)

# L189: 连接检测 → batch_create → 完全串行
suspicious_connections = AnomalyDetector.detect_connections(...)
SuspiciousConnection.batch_create(host_id, suspicious_connections)
```

**可行性判定**：完全可行。4 个无依赖步骤（进程/连接/启动项/注册表）可并行。注意：
- SQLite 是单线程写入，`batch_create` 不能并行写 → **分两阶段**：先并行检测（只计算不写库），再串行写库
- 第一阶段：`ThreadPoolExecutor` 同时跑 4 个 detector，`as_completed` 收集结果
- 第二阶段：按顺序写库

**建议方案**：
```python
# Phase 1: 并行检测（只计算）
with concurrent.futures.ThreadPoolExecutor(max_workers=4) as exe:
    fut_proc = exe.submit(AnomalyDetector.detect_processes, ...)
    fut_conn = exe.submit(AnomalyDetector.detect_connections, ...)
    fut_startup = exe.submit(AnomalyDetector.detect_startup_items, ...)
    fut_reg = exe.submit(...)  # 注册表提取
    # as_completed 收集
# Phase 2: 串行写库
AbnormalProcess.batch_create(...)
SuspiciousConnection.batch_create(...)
```

### #6 command_line 仍占 41%（59/133 规则）

| 维度 | 评估 |
|------|------|
| **优先级** | 🔴 P0 |
| **代码可行性** | ⚠️ **中等——需逐条审计** |
| **代码量** | ~50 行（规则调整） |
| **实施成本** | 中（1-2 天，含 59 条逐一评估） |
| **收益** | 🔥 大幅降低绕过风险 |

**现状确认**：
实测：59 条规则 `field: "command_line"`（来自 default_rules.json + process_enhancement_rules.json 合计）。规则引擎的 process 数据确实有 `name`、`path`、`command_line` 三个字段。

**可行性判定**：可行但工作量大。需逐条分类：

| 类别 | 数量（估算） | 建议 | 示例 |
|------|-------------|------|------|
| 纯进程名匹配 | ~25 | 迁移到 `name` 字段 | `powershell`、`certutil`、`cmd` |
| 路径匹配 | ~10 | 迁移到 `path` 字段 | `C:\Windows\Temp\*`、`%AppData%\*` |
| 参数模式 | ~15 | 保留 command_line | `-EncodedCommand`、`-urlcache` |
| 复合规则 | ~9 | 改用 composite + 双字段 | 进程名 + 参数 |

**示例迁移**：
```json
// 当前：纯 command_line，容易被改名绕过
{"field": "command_line", "pattern": "certutil\\.exe.*(-urlcache|-verify)"}
// 改为双字段复合校验：
{"logic": "AND", "sub_rules": [
  {"type": "regex", "field": "name", "pattern": "certutil\\.exe"},
  {"type": "regex", "field": "command_line", "pattern": "(-urlcache|-verify)"}
]}
```

### #8 无文件内容级检测

| 维度 | 评估 |
|------|------|
| **优先级** | 🟡 P1 |
| **代码可行性** | ⚠️ **低——需引擎 + 数据双改造** |

| **实施成本** | 高（2-3 天） |
| **收益** | ⭐ 增强 WebShell 检测能力 |

**现状确认**：
当前规则引擎支持 `regex`、`list`、`behavior`、`composite`、`exists`、`threshold` 六种类型。`field` 从 data_items 的属性中取值。如果要支持 `file_content`，需要：
1. 规则引擎 `_match_regex` 支持 `field=file_content` 字段
2. Agent 采集端上传文件内容（当前 agent 只会采集文件名和路径，不采内容）

**可行性判定**：**低可行性**，主要瓶颈在 Agent 端。当前 Agent 采集 JSON 中没有 `file_content` 字段。有三种路径：

| 路径 | 工作量 | 效果 |
|------|--------|------|
| **路径 A**：Agent 新增文件内容采集 | 高（Agent 端开发 + 协议升级） | 最好但最慢 |
| **路径 B**：规则引擎新增 `file_content` field（纯后端） | 中 | Agent 不给数据就没用 |
| **路径 C**：集成 YARA 扫描模块 | 中（~80 行） | 可独立运行，不依赖 Agent |

**建议**：暂缓 #8。先把 #6 做好（规则质量提升）比内容检测更紧迫。等 Agent 采集能力升级后再做。

### #17 规则版本管理

| 维度 | 评估 |
|------|------|
| **优先级** | 🟢 P2 |
| **代码可行性** | ⚠️ **中等——DB 改表 + 前端** |
| **代码量** | ~50 行 |
| **实施成本** | 中（1 天） |
| **收益** | ⭐ 容错能力 |

**现状确认**：
`rules` 表无 `version` 字段。修改规则后无法回滚。

**可行性判定**：中等可行。实现方式：
1. **轻量方案**（推荐）：`rules` 表加 `version INT DEFAULT 1`，前端编辑页加"版本历史"面板，每次保存 +1。回滚时复制旧版的 `condition`。
2. **完整方案**：新建 `rule_versions` 表存储全量历史版本。但数据量增长快（每条规则每次修改都备份）。

**建议**：采用轻量方案。`condition` 字段存 JSON 字符串，回滚就是覆盖旧 JSON + `version--`。

### #18 规则抑制期（已确认不反复告警）

| 维度 | 评估 |
|------|------|
| **优先级** | 🟢 P2 |
| **代码可行性** | ✅ **高** |
| **代码量** | ~50 行 |
| **实施成本** | 低（0.5 天） |
| **收益** | ⭐ 减少告警疲劳 |

**现状确认**：当前系统每次分析都检测所有已启用规则，无抑制机制。

**可行性判定**：完全可行。
1. 新建 `rule_suppression` 表：`{rule_name, host_id, suppressed_until(ISO datetime), reason, created_at}`
2. `RuleEngine.load_rules()` 过滤时跳过已抑制规则
3. 前端 `RulesView.vue` 加"抑制此规则 7 天"按钮
4. 规则管理页面可见已抑制规则的到期时间

### #19 behavior 规则无命中归属

| 维度 | 评估 |
|------|------|
| **优先级** | 🟢 P2 |
| **代码可行性** | ⚠️ **中等——需改造 `_match_behavior`** |
| **代码量** | ~30 行 |
| **实施成本** | 中（0.5-1 天） |
| **收益** | ⭐ 可追溯性 |

**现状确认**：
当前 behavior 规则匹配后返回的 `reason` 是文本字符串，没有结构化标注来自哪个维度（进程/网络/文件）。

**可行性判定**：中等可行。在 `_match_behavior()` 返回值中增加 `matched_dimension` 字段。但当前 35 个 behavior pattern 各自的命中逻辑不同，需要逐个补充。

**建议**：只对新增的 service behavior pattern 做命中归属标注，旧 pattern 逐步改造。

## 八、风险与建议

### 8.1 已知风险

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| #6 规则迁移可能导致误报/漏报 | 🔴 | 每条规则改完后必须做 regression test |
| #8 文件内容检测依赖 Agent 端改造 | 🔴 | 先做 YARA 集成（不依赖 Agent），Agent 改造单独排期 |
| #1 并行化时 SQLite 写锁竞争 | 🟡 | 采用两阶段策略：先并行读计算，再串行写 |
| #12 断路器集成可能导致 AI 分析静默降级 | 🟡 | 断路器打开时打 WARNING 日志，前端展示"AI 降级"状态 |
| 仪表盘数据量增长后查询变慢 | 🟡 | 预聚合表 + 缓存策略（30s TTL） |

### 8.2 关键建议

1. **一期先做 #1 + #12**：并行化效果立竿见影（分析速度快 2-3x），熔断/重试是 AI 模块的基本保障
2. **#6 规则迁移不要一步做完**：59 条 command_line 规则分 3 批改，每批改完跑一轮全量测试
3. **仪表盘不要和一期一起做**：仪表盘是纯新增功能，不影响核心检测流程。先让核心检测稳定下来
4. **#17 版本管理用轻量方案**：不要新建 `rule_versions` 表，简单加个 `version` 字段 + 回滚时覆盖 `condition` 就够了

### 8.3 与近期工作（服务检测统一）的关系

服务检测统一到规则管理（正在进行的 `service_detection_unify` 设计）与以上优化建议**没有冲突**，反而有协同效应：

| 优化项 | 与服务检测统一的关系 |
|--------|---------------------|
| #1 并行化 | service_risk 检测也需要并入并行管道 |
| #6 command_line | 服务检测不需要 command_line（用 path/name） |
| #10/16 规则统计 | 新增的 service 规则同样受益 |
| #18 规则抑制 | 同理适用于 service 规则 |
| #19 命中归属 | service behavior pattern 从一开始就加上命中归属标注 |
