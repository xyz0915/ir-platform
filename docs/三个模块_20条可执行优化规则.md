### R1 🔴 前端 API Token 通过 URL 查询参数明文暴露

**问题描述**：`frontend/src/api/ai.js:75` 和 `frontend/src/stores/ai.js:201` 中，EventSource（SSE 流式请求）将 JWT Token 拼接在 URL 中：
```javascript
const eventSource = new EventSource(
    `${baseURL}/ai/tasks/${taskId}/stream?token=${encodeURIComponent(token || '')}`
)
```
这导致 Token 出现在浏览器历史记录、服务器访问日志、Nginx 日志、HTTP Referer header 中，属于 **严重安全风险**。

**优化建议**：将 EventSource 替换为 fetch + `Authorization: Bearer` header 实现 SSE 读取（如 `stores/ai.js:207-213` 已正确实现的方式）。`streamAiAnalysis()` 和 `streamCompare()` 两处均需修复。

**优先级**：🔴 **高**

### R7 🟡 SSRF 风险 — `call_llm()` 的 URL 可被配置控制但未做白名单校验

**问题描述**：`ai_service.py:214-247` 中，`api_base_url` 来自用户配置的 Profile，直接作为 httpx client 的目标 URL。如果攻击者篡改了 API Base URL 配置，可诱导后端向任意内网地址发起 HTTP 请求（SSRF）。

**优化建议**：在 `call_llm()` 入口处添加 URL 校验：
```python
from urllib.parse import urlparse
parsed = urlparse(api_base_url)
if parsed.hostname in ("localhost", "127.0.0.1", "0.0.0.0") or parsed.scheme not in ("https",):
    raise ValueError(f"不安全的 API Base URL: {api_base_url}")
```
或在配置模型中增加 URL Scheme 白名单（仅允许 `https://`）。

**优先级**：🟡 **中**

### R9 🔴 `_match_behavior()` 496 行巨型 if-elif 链 — 需策略模式重构

**问题描述**：`rule_engine.py:1001-1497` 的 `_match_behavior()` 是一个 496 行的 if-elif 链，处理 **35+ 种行为模式**。每种模式都是一个独立的检测逻辑块，但全部嵌套在一个方法中。新增模式需修改此方法（开闭原则违反）。

**优化建议**：采用策略模式 + 注册表：
```python
# 注册表
_BEHAVIOR_HANDLERS: dict[str, Callable] = {}

def register(pattern: str):
    def decorator(func):
        _BEHAVIOR_HANDLERS[pattern] = func
        return func
    return decorator

# 各模式独立定义（可放在单独文件中）
@register("orphan_process")
def _match_orphan_process(data_item, condition, ctx) -> bool: ...

# _match_behavior 简化为 5 行
def _match_behavior(self, data_item, condition, ctx):
    handler = _BEHAVIOR_HANDLERS.get(condition.get("pattern"))
    return handler(data_item, condition, ctx) if handler else False
```

**优先级**：🔴 **高**

### R16 🔴 `ancestor_map` 构建逻辑在 2 个文件中重复实现

**问题描述**：`anomaly_detector.py:100-124` 和 `process_event_consumer.py:166-190` 中，完全相同的 `ancestor_map` 构建算法独立实现两次（从 ppid 回溯、遇到 0/1/4 停止、深度限制 10 层、环形检测）。新增第 3 个需要 ancestor_map 的检测器将再次重复。

**优化建议**：提取到 `app/analysis/utils.py`：
```python
def build_ancestor_map(processes: list[dict], pid_to_proc: dict[int, dict], max_depth: int = 10) -> dict[int, list[int]]:
    """构建进程祖先链映射，回溯 ppid 直到 0/1/4 或达最大深度."""
    ancestor_map: dict[int, list[int]] = {}
    for pid, proc in pid_to_proc.items():
        chain: list[int] = []
        current = proc.get("ppid") or proc.get("parent_pid")
        seen: set[int] = set()
        for _ in range(max_depth):
            if current is None or current in (0, 1, 4) or current in seen:
                break
            chain.append(current)
            seen.add(current)
            parent = pid_to_proc.get(current)
            current = parent.get("ppid") if parent else None
        ancestor_map[pid] = chain
    return ancestor_map
```
两处调用此函数替换重复实现。

**优先级**：🔴 **高**

### R20 🟢 `incident_id` 使用 Python `hash()` 跨进程不稳定

**问题描述**：`anomaly_detector.py:655,673` 中，通过 `hash(tuple(sorted(related_findings)))` 和 `hash((s["finding_id"], idx))` 生成 incident/alert ID。Python 内置 `hash()` 在不同进程间 seed 不同（Python 3.3+），且 64 位系统的 `hash()` 值范围为 64 位，拼接 `"INC-" + str(abs(hash(...)))` 理论上可能碰撞。

**优化建议**：改用 `hashlib.md5` 生成稳定 ID：
```python
import hashlib
incident_id = "INC-" + hashlib.md5(
    json.dumps(sorted(related_findings), sort_keys=True).encode()
).hexdigest()[:12]
```
这样 ID 在不同进程、不同机器间均稳定一致。

**优先级**：🟢 **低**
