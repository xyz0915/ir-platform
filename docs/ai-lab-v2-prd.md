# IR 应急响应平台 — AI 实验室 v2.0 产品需求文档

## 项目信息

| 项目 | 内容 |
|------|------|
| **Language** | 中文 |
| **Programming Language** | 后端 Python (FastAPI) + 前端 Vue 3 (Element Plus + MUI + Tailwind CSS) |
| **Project Name** | ai_lab_v2 |
| **原始需求** | IR 应急响应平台自然语言指挥台重大版本升级（v2.0），包含 9 项功能增强，目标是将自然语言指挥台打造成平台的默认操作入口和产品亮点。当前指挥台已完成基础建设：多轮上下文、时间解析、结果下钻、会话持久化、AI 研判、LLM 回复、元宝风格排版。 |

---

## 一、产品目标

让自然语言指挥台成为应急响应的 **"默认操作入口"**——分析师遇到安全事件后，第一反应是打开指挥台输入自然语言问题，**70% 的日常调查任务通过对话完成**，而不再需要手动翻查多个页面。

## 二、用户故事

### P0-❶ 流式回复 + 富卡片混合渲染

| 角色 | 需求 | 价值 |
|------|------|------|
| 安全分析师 | 我提问后能看到 AI 逐字输出回复，而不是等待全部生成后才显示 | 减少等待焦虑，即时获得部分信息 |
| 安全分析师 | 我希望 AI 回复中能内嵌可交互的统计图、告警列表等富卡片，而不只是纯文本 | 信息更直观，无需再手动跳转页面查看 |
| SOC 负责人 | 我希望流式渲染不阻塞卡片渲染，AI 生成文本和卡片可穿插出现 | 兼顾实时性和信息密度 |

### P0-❷ 可执行对话

| 角色 | 需求 | 价值 |
|------|------|------|
| 安全分析师 | 我直接说"封锁 1.2.3.4"，AI 就能调用防火墙 API 执行阻断并返回结果 | 避免手动翻页面操作，缩短 MTTR |
| 应急响应人员 | 我希望 AI 执行操作前主动向我确认高危动作，防止误操作 | 操作安全可控 |
| 安全分析师 | 我希望执行结果以状态卡片形式展示在对话中，包含成功/失败和执行详情 | 执行结果可回溯、可审计 |

### P0-❸ 上下文指示器

| 角色 | 需求 | 价值 |
|------|------|------|
| 安全分析师 | 我希望在输入区上方看到当前对话上下文（如 "📌 当前：web-01"），避免"AI 忘了我在查哪台主机" | 对话上下文可感知、可控制 |
| 安全分析师 | 我希望可以手动切换分析的主机上下文，而不用每次重新输入主机名 | 提升连续调查效率 |
| 安全分析师 | 我希望可以固定/清空当前上下文 | 灵活控制对话状态 |

### P1-❹ 调查剧本

| 角色 | 需求 | 价值 |
|------|------|------|
| 安全分析师 | 我遇到登录失败事件时，点击"调查登录失败"剧本，AI 自动按预置步骤逐一调查并输出每步结果 | 降低新手分析师的调查门槛，确保调查全面性 |
| 高级安全分析师 | 我希望可以暂停剧本、查看当前进度、跳过某个不相关的步骤 | 灵活控制调查流程 |

### P1-❺ 会话摘要

| 角色 | 需求 | 价值 |
|------|------|------|
| 安全分析师 | 我切换会话后，旧会话自动生成摘要卡片，包含调查目的、发现和操作 | 方便回顾和分享调查过程 |
| SOC 负责人 | 我在会话历史列表中能看到摘要预览，快速判断哪个会话值得复看 | 提升会话历史利用率 |

### P1-❾ 可信度溯源

| 角色 | 需求 | 价值 |
|------|------|------|
| 安全分析师 | 我希望 AI 每条回复都标注可信度（高/中/低），低可信度时显示"建议核实"提示 | 避免盲目信任 AI 结论 |
| 安全分析师 | 我希望 AI 引用的日志 ID/告警 ID 可点击反查详情 | 快速验证 AI 结论的准确性 |

### P2-❸ 热力图+时间轴

| 角色 | 需求 | 价值 |
|------|------|------|
| 安全分析师 | 我希望会话侧边栏显示异常事件热力图，红色柱状条表示异常峰值 | 快速感知异常分布时间段 |

### P2-❼ 攻击路径图

| 角色 | 需求 | 价值 |
|------|------|------|
| 安全分析师 | 我希望 AI 分析后以 SVG 路径图展示攻击链路（如 "web-01 → jump-box → DC-01"） | 一目了然理解攻击传播路径 |

### P2-❽ 多模态输入

| 角色 | 需求 | 价值 |
|------|------|------|
| 安全分析师 | 我希望直接把 .evtx 文件拖入聊天框，AI 自动解析文件内容并分析 | 减少文件上传→导入→查询的繁琐流程 |

**可信度规则**：

| 场景 | 可信度 | 行为 |
|------|--------|------|
| 数据充分 + 高置信度模式匹配 | 🟢 高 | 直接呈现结论 |
| 部分数据缺失或模式模糊 | 🟡 中 | 建议补充数据 |
| 单数据源或推理链薄弱 | 🔴 低 | 自动追加"建议核实"提示，高亮引用 ID |

**关键行为**：
- 新增 `<ConfidenceBadge>` 组件，固定在 AI 消息右上角
- 后端返回每条消息携带 `confidence` 字段
- 日志 ID/告警 ID 渲染为 `<a>` 标签，点击跳转对应详情页

## 五、数据流与接口设计

### 5.1 流式回复 SSE 接口

**端点**：`POST /ai/query-stream`

**请求**：
```json
{
  "query": "web-01 的告警有哪些",
  "session_id": "abc123",
  "context": {
    "host_id": 1,
    "host_name": "web-01",
    "time_range": { "start": "2024-07-05T00:00:00Z", "end": "2024-07-06T00:00:00Z" }
  },
  "files": [
    { "name": "security.evtx", "type": "evtx", "content_base64": "..." }
  ]
}
```

**响应**（SSE 流）：
```
event: query_start
data: {"session_id": "abc123", "intent": "alerts", "confidence": 0.85}

event: text_chunk
data: {"type": "text", "content": "根据分析，web-01 在过去24小时内"}

event: text_chunk
data: {"type": "text", "content": "出现了以下异常行为："}

event: card
data: {"type": "card", "card_type": "alert_list", "data": {"alerts": [...], "summary": "共 3 条告警"}, "action_hints": ["block_ip", "isolate_host"]}

event: text_chunk
data: {"type": "text", "content": "其中严重级别告警包括以下条目。"}

event: card
data: {"type": "card", "card_type": "stats_chart", "data": {"labels": ["08:00","09:00","10:00"], "values": [2,5,12]}, "chart_type": "bar"}

event: query_end
data: {"session_id": "abc123", "usage": {"prompt_tokens": 1200, "completion_tokens": 350}, "confidence": "high", "source_ids": ["alert-1024", "alert-1025"], "attack_path": null}
```

**SSE 事件类型**：

| 事件名 | 用途 | 字段 |
|--------|------|------|
| `query_start` | 流开始，携带元信息 | `session_id`, `intent`, `confidence` |
| `text_chunk` | 文本内容块 | `type: "text"`, `content` |
| `card` | 富卡片内容块 | `type: "card"`, `card_type`, `data`, `action_hints` |
| `action_confirm` | 操作确认请求 | `action`, `target`, `reason`, `confirm_id` |
| `action_result` | 操作执行结果 | `action`, `status`, `result`, `exec_time_ms` |
| `playbook_progress` | 剧本执行进度 | `step`, `total`, `current_step_name`, `status` |
| `query_end` | 流结束，携带汇总信息 | `session_id`, `usage`, `confidence`, `source_ids`, `attack_path` |

**前端消费**：
```javascript
// 伪代码
const response = await fetch('/ai/query-stream', { method: 'POST', body: JSON.stringify(params), headers: {'Content-Type': 'application/json'} })
const reader = response.body.getReader()
const decoder = new TextDecoder()

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  const text = decoder.decode(value)
  // 解析 SSE data: 行
  const lines = text.split('\n')
  for (const line of lines) {
    if (line.startsWith('data: ')) {
      const data = JSON.parse(line.slice(6))
      handleStreamEvent(data)
    }
  }
}
```

## 七、待确认问题

### 技术选型

| # | 问题 | 选项 | 建议 |
|---|------|------|------|
| Q1 | 流式传输协议选择 | **SSE** vs WebSocket | **推荐 SSE**：后端子啊已有 StreamingResponse 支持，前端 `EventSource` 或 `fetch` + `ReadableStream` 均可，比 WebSocket 更轻量，且无双向通信需求 |
| Q2 | 攻击路径图渲染方式 | **SVG** vs Canvas vs D3.js | **推荐 SVG**：节点数通常 < 10，SVG 交互性好（可点击、hover），无需引入额外依赖，可嵌入消息流 |
| Q3 | 富卡片渲染策略 | **数据驱动** vs 预定义组件注册表 | **推荐预定义组件注册表**：`<StreamCard cardType="stats">` 注册表模式，新增卡片类型只需注册无需改消息流逻辑 |
| Q4 | 文件上传方式 | **base64** vs multipart/form-data | 小文件（<10MB）用 **base64** 更方便，流式传输可一起发送；大文件用 multipart 分步上传 |
| Q5 | 剧本执行引擎 | **后端异步任务** vs LLM ReAct | **后端异步任务** + LLM 辅助分析：剧本步骤固化，LLM 负责每步的分析内容 |
| Q6 | 会话摘要生成时机 | **切换时同步** vs 离线异步 | **切换时同步调用**（轻量 LLM 调用）+ 本地结构化兜底，保证摘要即时可见 |
| Q7 | 热力图数据来源 | **前端本地计算** vs 后端接口 | **前端本地计算**：基于 `chatMsgs` 中的时间戳和告警数量，无需新增接口 |
| Q8 | 流式重连策略 | **自动重连** vs 用户手动刷新 | **自动重连 3 次**：连接断开后自动重连，已有内容保留，新内容追加 |

### 架构决策

| # | 问题 | 说明 |
|---|------|------|
| Q9 | SSE 流中卡片数据的传输粒度 | 卡片是作为独立 event 还是嵌在 text_chunk 中？**建议独立 event**，便于前端单独渲染 |
| Q10 | 可执行对话的权限控制 | 是否需要区分角色的执行权限？v2.0 暂不区分，所有分析师均可执行 |
| Q11 | 攻击路径图的来源 | AI 分析生成 vs 本地规则引擎？**AI 分析为主**，本地规则作为兜底 |
| Q12 | 多模态文件解析 | .evtx 解析在服务端子啊实现？**建议后端子啊服务**复用已有 `log_importer.py` |

## 八、实施建议

### 分阶段实施计划

| 阶段 | 功能 | 预估工时 | 交付价值 |
|------|------|----------|----------|

| **Phase 2** | P0-❷ 可执行对话 + P1-❾ 可信度溯源 | 2 周 | 从查看→操作闭环，降低 MTTR |
| **Phase 3** | P1-❹ 调查剧本 + P1-❺ 会话摘要 | 2 周 | 提升调查流程化和可回溯性 |

### 风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| LLM 流式响应不稳定（中断/超时） | TTFB 不稳定，用户体验差 | 中 | 前端自动重连，后端超时降级为非流式 |
| Action API 调用失败 | 可执行对话不可用 | 中 | 返回错误原因 + 建议手动操作 |
| 多轮上下文丢失 | AI 回答不准确 | 低 | 上下文指示器可视化 + 手动修正 |
| 剧本执行耗时过长 | 用户等待不耐烦 | 中 | 实时进度展示 + 支持跳过步骤 |
